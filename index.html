Self-Hosted PaaS with Raft-Based Distributed Scheduler

GoPythonFastAPIPostgreSQLKubernetescontroller-runtimeKanikoAWS EKSECRTerraformHelmPrometheusGrafanaOpenTelemetryGitHub Actions

Heroku-style platform where a git push goes live in 23 seconds on AWS EKS. At its core is a distributed job scheduler written from scratch in Go, with Raft leader election (pre-vote and check-quorum, no Raft library). It lost zero jobs and produced zero duplicate side effects across 32,352 jobs and 87 injected faults (leader kills, process freezes, network partitions), on a laptop, in GitHub Actions, and on AWS EKS spot nodes, with a median leader failover of 0.7–1.1 seconds. Postgres fencing epochs make a deposed leader harmless, and a completion commits only if its lease token is still current, with its effects and follow-up jobs written in the same transaction, which guarantees exactly-once completion. Heartbeat leases, retries with jittered exponential backoff, and a dead-letter queue round out the scheduler. Porting it from Python to Go cut scheduler CPU by 34–48% and memory by 57–60% in back-to-back runs with the same fault schedule, while keeping the wire protocol, metric names, and trace spans identical. A Go Kubernetes operator (controller-runtime, App and Release CRDs, server-side apply) runs build → deploy → verify: images are built in the cluster with Kaniko and pushed to ECR through IRSA with no static credentials, and a broken release rolls back automatically, keeping 100% of requests on the last healthy version. EKS is provisioned with Terraform (87 resources) and pinned Helm charts for Prometheus and Grafana, and the platform kept running through a real EC2 spot interruption. Verification includes 106 race-detected Go tests at 92.4% coverage, Raft tests on a simulated network, an envtest operator suite, and a chaos harness that caught 4 latent bugs, including a primary-key violation that wedged the job queue and an EKS ingress misconfiguration that dropped about 45% of requests. The design is documented in 8 Architecture Decision Records.

Real-Time Collaborative Code Review Platform

RustTokioAxumYjs (yrs)PythonFastAPIReactTypeScriptMonacoPostgreSQLRedis StreamsAWS EKSRDSElastiCacheKubernetesKEDATerraformHelmGitHub Actionsk6

Cloud-native platform for sharing code, reviewing it, and editing together in real time. The real-time backend was rewritten from Python to Rust (tokio, axum, and Yjs CRDTs via yrs), with one actor per open document so connections never share locks. In load tests on AWS EKS it held 2,200 concurrent connections per 0.5-CPU pod at a p99 latency under 200 ms (44–124 ms across 6 runs) and delivered at least 99.99% of messages; on identical pods, the Python version held 800. Document-affinity routing and per-document Redis Streams cut cross-pod p99 latency from 104 ms to 6 ms. Edits are persisted as Postgres snapshots plus a batched update log, with Redis Stream replay, graceful drain, and KEDA autoscaling on connection count. No edits were lost (0 of 10,038 on EKS) while scaling from 2 to 10 pods and back, and killing the pod that hosted a live document lost 0 of 3,483 edits, with clients reconnected within 1.9 seconds. Autoscaling on AWS exposed an RDS connection-exhaustion bug that stalled clients for up to 153 seconds; a per-pod connection budget and a larger instance cut peak connections from 79 to 35. Profiling also removed a latency tail caused by a missing TCP_NODELAY and cut memory per idle connection 5x (from 148.5 to 29.7 KiB). The FastAPI service issues 60-second, single-use WebSocket tickets bound to one document, and the React and TypeScript frontend uses the Monaco editor with live shared cursors. The infrastructure (EKS on Graviton, RDS, ElastiCache, a network load balancer, ECR, and Secrets Manager; 125 resources) is defined in Terraform and Helm and deployed through keyless GitHub OIDC CI/CD, with Prometheus, Grafana, and Alertmanager for monitoring. The Rust server has 84 tests at 87.6% coverage, including CRDT convergence property tests and testcontainers integration tests.

Multi-Tenant Serverless Log Pipeline

PythonFastAPIAWS LambdaAPI GatewaySQSDynamoDBCloudWatchTerraformGitHub Actions

Event-driven, multi-tenant log ingestion pipeline on AWS serverless (API Gateway → Lambda → SQS → Lambda → DynamoDB), migrated from an earlier GCP version (Cloud Run, Pub/Sub, Firestore) without changing API behavior, retry semantics, or tenant isolation. It handled 6,000 requests per minute at 84 ms p95 latency with 100% success, 6× the requirement, and scales to $0 when idle. A verification script read every accepted log back from DynamoDB and confirmed that zero messages were lost across 15,000 load-test requests. Crash recovery uses partial-batch failure reporting, exponential backoff, and a dead-letter queue, and because ingestion is separated from processing, the API absorbed a 9,623-message traffic spike with zero 5xx errors. Tenants are isolated with DynamoDB partition keys (zero cross-tenant leaks), phone numbers are redacted in more than 8 formats, and the stack is secured with least-privilege IAM and permissions boundaries, SQS encryption, DynamoDB point-in-time recovery, and API Gateway throttling. All 33 AWS resources are defined in Terraform, with deterministic Lambda builds, versioned aliases for one-command rollbacks, and GitHub Actions CI/CD that uses keyless OIDC, runs smoke tests after each deploy, and rolls back automatically on failure. It has 38 unit tests at 93% coverage and 9 CloudWatch alarms with SNS email alerts.

Healthcare Operations Automation Platform

PythonFastAPICeleryRedisPostgreSQLLlama 3.1GPT-4oLiveKitNext.jsReactHashiCorp VaultDockerNginx

Automated a pain clinic's 8-step patient intake, from referral email to EHR registration, e-signed lien, and appointment call, across 10 integrated systems with a multi-agent LLM pipeline (FastAPI, Celery/Redis, Llama 3.1). Separate LLM agents validate referral emails and extract 10 patient and attorney fields from them, behind a 5-stage filter that keeps irrelevant mail away from the model. An outbound AI phone agent (LiveKit Agents, GPT-4o, gpt-4o-transcribe) confirms patient identity, records pain scores, and books appointments at 5 clinic locations, with retries, SMS follow-ups, and handoff to a human on request. A fax pipeline reads both digital and scanned faxes (PyMuPDF, with a Tesseract OCR fallback) from 7 Office 365 shared mailboxes and processes each fax exactly once across sharded workers using SHA-256 Redis deduplication. Patients are registered in the PrognoCIS EHR through its REST API, signed lien PDFs are uploaded automatically, and DocuSeal sends pre-filled e-signature forms. Designed the PostgreSQL data model (11 tables) behind 43 FastAPI endpoints, and built Next.js and React dashboards: a fax action table, admin and patient portals, and an agent-health page fed by Redis heartbeats. Six services run in Docker behind Nginx with TLS and deploy with one command. Secrets live in a self-unsealing HashiCorp Vault, dates of birth are encrypted at rest, and accounts and traffic are protected with TOTP 2FA, JWT role-based access, audit logging, and HMAC-SHA256 request signing.
